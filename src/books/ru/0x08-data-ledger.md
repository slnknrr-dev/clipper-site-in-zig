## Записи участников: журнал и B+ дерево

### Развилка

Где лежит всё, что пишут участники: учётные записи, сеансы, права, комментарии, форумы, доски, черновики, цитаты, закладки, настройки. Это данные третьей ступени: их нельзя восстановить, если потеряли.

### Пути

1. **Реляционная база** (SQLite и подобные).
2. **Файл на каждую сущность** — комментарий как файл, тема как папка.
3. **Свои структуры в памяти** со своим форматом сохранения для каждой.
4. **Одно упорядоченное хранилище «ключ-значение»** под всё.

И внутри пути 4 — как устроено само хранилище:

- **журнал**: файл, в который только дописывают, а всё состояние — в памяти;
- **B+ дерево** с копированием при записи: читается с диска по запросу;
- **LSM-дерево**: запись в память и журнал, периодический сброс в отсортированные файлы и их слияние.

### Выбор

Одно хранилище «ключ-значение» с пятью операциями: взять, положить, удалить, пройти по префиксу, сбросить на диск. Ключ — буква вида и номер: `U1001` — участник, `Q17` — цитата, у комментария в ключе стоят номер книги и номер комментария, поэтому все комментарии одной книги лежат подряд. Значение — поля через управляющий символ. Вся «схема базы» — одна таблица букв в начале `src/db.zig`.

Почему одно на всё: у сайта нет запросов, которым нужно больше. Комментарии к книге — проход по префиксу. Темы форума — проход по префиксу. Сеанс по cookie — взять по ключу. Соединений таблиц нет, потому что каталог лежит в снимке.

Под интерфейсом — два хранилища на выбор при запуске.

**Журнал** (по умолчанию). Текстовый файл; каждая строка — одна операция: плюс, ключ, значение и контрольная сумма либо минус, ключ и сумма. Из одного правила «только дописывать» следует почти всё: запись, оборванная сбоем, — всегда последняя строка, и читатель останавливается перед ней; порча посреди файла — строка с неверной суммой, она пропускается и считается; формат читается глазами и чинится текстовым редактором. В памяти — отсортированный массив и двоичный поиск.

**B+ дерево** (`-btree`). Страница, до которой можно дойти от корня, никогда не переписывается: изменение копирует путь от листа до корня, а какой корень действует, говорят две мета-страницы, которые пишутся по очереди. Сбой в любой момент оставляет прежнее дерево целым — по построению.

Почему два. Журнал прост и быстр, но держит всё в памяти и при старте читает файл целиком. Дерево стартует мгновенно и не держит лишнего, но сложнее в разы: семьсот строк против двухсот восьмидесяти. Правильный ответ зависит от размера сайта, и угадывать заранее не нужно: интерфейс один, записи одни и те же, тест прогоняет одну историю через оба и сравнивает.

### Тупики

**Файл на сущность (путь 2).** Выглядит просто, но файловая система — плохая база: сотни тысяч мелких файлов, атомарность только на уровне переименования, обход папки без порядка. Тупик при любом заметном объёме.

**Свои структуры на каждую сущность (путь 3).** Десять форматов, десять способов сохранить, десять способов испортить при сбое. Одно хранилище — один способ.

**Переписывать файл целиком при каждом изменении.** Надёжно (запись во временный файл и переименование), но цена записи растёт с размером данных. Тупик после первой тысячи записей.

### Лучше — при других условиях

**LSM-дерево — при частой записи.** Журнал только растёт: удалённая запись остаётся в нём навсегда вместе со строкой об удалении. Сеансы, которые создаются и гаснут, нити досок, живущие час, — всё копится. LSM решает это слиянием: старые версии ключей выбрасываются при сбросе на диск. При десятках тысяч записей в день LSM лучше журнала и лучше B+ дерева (у дерева каждое изменение копирует три-четыре страницы). Клиппер не дошёл до этой нагрузки, и LSM — самая сложная из трёх структур.

**Уплотнение журнала — минимальное улучшение.** Переписать журнал, оставив только последние значения живых ключей, — сотня строк. Это не сделано, и это известная дыра: для сайта с активными досками файл придётся когда-нибудь переписать вручную.

**Вторичные индексы — при модерации.** «Все сообщения, ждущие проверки» в хранилище «ключ-значение» — полный проход. Лучше — дописывать второй ключ вида «состояние, номер» и вести его при каждом изменении. Это ровно та сложность, о которой говорила ось: ступень 4 приносит в хранение то, без чего ступень 3 обходится.

**SQLite — при снятом запрете на чужой код.** Честно: для большинства сайтов такого размера это лучший выбор. Он решает уплотнение, индексы, транзакции и проверен десятилетиями. Клиппер его не берёт потому, что рамка запрещает чужой код и требует запуска на XP без библиотеки C.

### Цена

Нет запросов «найди все, где...»: любой поиск не по префиксу ключа — полный проход. Значения — строки с разделителями без схемы: добавить поле в конец легко, переставить — значит написать преобразование старых записей. Сброс на диск при каждой записи — потолок скорости: запись упирается в диск, и несколько процессов её не ускоряют.

Освободившиеся страницы дерева не используются повторно: файл уплотняется только при открытии. Теста, который обрывает запись дерева посреди транзакции, нет — для журнала такой тест есть, для дерева «переживает сбой» остаётся обещанием конструкции.
