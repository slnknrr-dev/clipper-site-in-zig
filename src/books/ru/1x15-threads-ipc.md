## Потоки, процессы и общение между ними

### Вопрос: потоки или процессы?

У сервера, который хочет занять несколько ядер, два пути. Потоки делят память: быстро обмениваться, легко испортить чужое. Процессы делят только то, что им явно дали: медленнее обмениваться, но падение одного не трогает других. В Zig есть и то и другое, и выбор между ними — архитектурный, а не синтаксический.

### Потоки в стандартной библиотеке

```
const std = @import("std");

fn work(counter: *std.atomic.Value(u64), n: u64) void {
    for (0..n) |_| _ = counter.fetchAdd(1, .monotonic);
}

pub fn main() !void {
    var counter = std.atomic.Value(u64).init(0);
    var threads: [4]std.Thread = undefined;
    for (&threads) |*t| t.* = try std.Thread.spawn(.{}, work, .{ &counter, 100_000 });
    for (threads) |t| t.join();
    std.debug.print("{d}\n", .{counter.load(.monotonic)}); // 400000
}
```

`std.Thread.spawn` принимает функцию и кортеж аргументов; типы проверяются при компиляции. `std.atomic.Value(T)` — атомарная переменная, и порядок памяти (`.monotonic`, `.acquire`, `.release`, `.seq_cst`) указывается явно при каждой операции. Язык не выбирает его за вас: самый строгий порядок медленнее, самый слабый — легко ошибиться.

Для всего, что сложнее счётчика, есть `std.Thread.Mutex`, `std.Thread.RwLock`, `std.Thread.Condition`, `std.Thread.Pool`.

Нет «безопасной передачи между потоками» на уровне типов, как `Send` и `Sync` в Rust. Гонку данных компилятор не найдёт. Её найдёт только внимательность или санитайзер потоков при сборке C-части. Это прямое следствие отказа от модели владения.

### Почему Клиппер однопоточный

Первая причина — устройство: запрос короткий, второй поток не ускорит его, а блокировки на общее состояние сделают сервер сложнее (книга 0, страница о цикле событий).

Вторая причина — Windows XP. `std.Thread.Mutex` на Windows построен на SRW-блокировках, которые появились в Vista. Программа, вызвавшая такой мьютекс, на XP не запустится: загрузчик не найдёт функцию. Поэтому сервер собирается с `.single_threaded = true` — тогда стандартная библиотека убирает блокировки целиком.

Потоки в проекте всё же есть — в инструменте замера нагрузки `tools/load.zig`. Он собирается под машину сборки, а не под XP, и может себе позволить шестьдесят четыре потока с атомарным счётчиком оставшихся запросов.

### Процессы и общение между ними

Чтобы занять несколько ядер без потоков, Клиппер запускает несколько процессов (`-w N`). Им нужно договариваться, и вот чем они пользуются — это хороший перечень приёмов межпроцессного общения без единой очереди сообщений:

| приём | Linux | Windows | зачем |
| общий слушающий сокет | наследуется через fork | наследуется через CreateProcessW | все принимают соединения |
| номер сокета и прочее | память после fork | флаг командной строки --worker | воркер знает, что ему дали |
| общий файл хранилища | файл | файл | данные |
| блокировка файла | flock | LockFileEx | очередь записей |
| общий снимок | mmap одного файла | MapViewOfFile одного файла | каталог в одной физической памяти |
| шлюз приёма | не нужен | системный мьютекс | только один процесс ждёт accept |
| жив ли главный | getppid | WaitForSingleObject на дескрипторе | воркер уходит вслед за главным |

Самое интересное здесь — что всё общение идёт через файлы и системные объекты, а не через сообщения. Воркер не спрашивает соседей, что изменилось: он дочитывает журнал с места, где остановился. Это медленнее, чем общая память, но не требует никакого протокола и переживает падение любого участника.

### Вопрос: почему на Windows дескриптор передаётся строкой?

На Linux после `fork` потомок — копия родителя, и все переменные на месте. На Windows `fork` нет. Новый процесс начинается с нуля, и единственное, что можно ему передать, — унаследованные дескрипторы и командная строка. Поэтому номер сокета, номер главного процесса и дескриптор шлюза записываются числами в флаг `--worker`, а воркер превращает числа обратно в дескрипторы. В Zig это одна строка: `@ptrFromInt(число)`.

### Цена

Процессы дороже потоков по памяти: у каждого свои буферы и кэши. Обмен через файл медленнее обмена через память. Запись не масштабируется: процессы пишут по очереди. Зато ни одной гонки данных в памяти — потому что общей памяти, в которую пишут, нет.
