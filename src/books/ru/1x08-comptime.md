## comptime: тот же язык при компиляции

### Вопрос: зачем ещё один язык для шаблонов и обобщений?

В C обобщённый код пишут макросами — языком, который ничего не знает о типах. В C++ — шаблонами, которые со временем стали отдельным языком со своими правилами. В Rust — обобщениями с ограничениями плюс макросами для всего, что в обобщения не влезло.

Zig отвечает так: никакого второго языка. Любой код Zig можно выполнить при компиляции, если всё, что ему нужно, известно при компиляции. Слово `comptime` это требует.

### Типы — значения

```
fn Pair(comptime T: type) type {
    return struct { a: T, b: T };
}

const P = Pair(u32);
const p = P{ .a = 1, .b = 2 };
```

`Pair` — обычная функция, которая принимает тип и возвращает тип. Обобщённые структуры стандартной библиотеки (`ArrayList(T)`, `HashMap(K, V)`) устроены именно так. Нет отдельного синтаксиса для обобщений: есть функции и значения типа `type`.

### Строки, которые обрабатываются при сборке

Самый наглядный пример из Клиппера — шаблоны страниц. Файл шаблона встраивается в программу (`@embedFile`) и режется по меткам `{{имя}}` при компиляции:

```
pub fn render(comptime src: []const u8, w: *W, ctx: anytype) void {
    comptime var rest: []const u8 = src;
    inline while (true) {
        const open = comptime std.mem.indexOf(u8, rest, "{{") orelse break;
        const close = comptime std.mem.indexOfPos(u8, rest, open, "}}")
            orelse @compileError("шаблон: не закрыто {{");
        if (open > 0) w.raw(comptime cp.lit(rest[0..open]));
        const name = comptime rest[open + 2 .. close];
        @field(@TypeOf(ctx.*), name)(ctx, w);
        rest = comptime rest[close + 2 ..];
    }
    if (rest.len > 0) w.raw(comptime cp.lit(rest));
}
```

`std.mem.indexOf` — та же функция, что работает при выполнении. `inline while` разворачивается: цикла в программе нет, есть прямая последовательность «записать кусок, вызвать метод». `@field(Тип, имя)` находит метод по имени из шаблона; если метода нет — ошибка сборки. `@compileError` — сообщение об ошибке, которое пишет сам программист.

### Рефлексия

`@typeInfo(T)` возвращает описание типа как обычную структуру: поля, их типы, варианты перечисления. По ней можно пройти `inline for` и сгенерировать код:

```
fn countFields(comptime T: type) usize {
    return @typeInfo(T).@"struct".fields.len;
}
```

Так в стандартной библиотеке устроены форматирование, сериализация JSON и сравнение в тестах.

### Где граница

**Время сборки.** Интерпретатор компилятора медленный. Каждая операция при компиляции стоит в сотни раз дороже, чем при выполнении. Отсюда `@setEvalBranchQuota`: без неё компилятор остановит долгое вычисление, решив, что оно зациклилось. В Клиппере перекодировка всех строк интерфейса при компиляции — заметная часть минуты, которую занимает сборка.

**Большие данные.** Встроенные книги (эта в их числе) сначала хотелось разбирать из Markdown при компиляции. Отказались: сто пятьдесят килобайт текста интерпретатор переваривал бы долго и при каждой сборке. Вместо этого — отдельная программа, которую система сборки запускает как шаг и кэширует результат. Правило: при компиляции — то, что мало и связано с типами; большое и линейное — шагу сборки.

**`anytype`.** Параметр без типа принимает что угодно, и проверка случается внутри функции. Ошибка выглядит как цепочка из нескольких уровней вызовов, и читать её надо уметь. Это утиная типизация, проверяемая компилятором: удобно, но договор о том, что нужно от типа, нигде не записан.

### Почему это решение принципиальное

Многие языки разделяют «язык программы» и «язык метапрограммы». Zig сознательно их сливает. Цена — медленный интерпретатор и сообщения об ошибках, которые трудно читать. Выигрыш — не нужно учить второй язык, и метапрограмма отлаживается теми же средствами, что программа. Из всех решений языка это, пожалуй, самое смелое и самое последовательное.
