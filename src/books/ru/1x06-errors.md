# Часть II. Три столпа

## Ошибки как значения

### Вопрос: почему нет исключений?

Исключение — скрытый поток управления. Строка `parse(x)` в языке с исключениями может выйти из функции в середине, и по тексту этого не видно. Для сервера, который держит открытые файлы, блокировки и буферы, каждая такая невидимая точка выхода — место для утечки или незакрытой блокировки.

Zig выбирает другое: ошибка — значение, возвращаемое вместе с результатом, а каждая точка, где ошибка может прервать функцию, помечена словом `try`.

### Наборы ошибок

```
const ParseError = error{ Empty, NotNumber, TooBig };

fn port(s: []const u8) ParseError!u16 {
    if (s.len == 0) return error.Empty;
    const n = std.fmt.parseInt(u32, s, 10) catch return error.NotNumber;
    if (n == 0 or n > 65535) return error.TooBig;
    return @intCast(n);
}
```

`ParseError!u16` — «либо одна из трёх ошибок, либо число». Набор ошибок — тип, и компилятор знает его целиком. Если написать `!u16` без набора, компилятор выведет его сам из тела функции.

Вызывающий выбирает:

- `try port(s)` — ошибку передать наверх;
- `port(s) catch 8080` — значение по умолчанию;
- `port(s) catch |e| switch (e) { ... }` — разобрать каждую; `switch` обязан покрыть все варианты набора.

Последний пункт — главное отличие от кодов возврата C: нельзя забыть случай. Добавили в функцию новую ошибку — компилятор покажет каждый `switch`, где она не разобрана.

### Ошибка или «ничего»

`!T` и `?T` — разные вещи, и хороший код их различает. В Клиппере разбор заголовка `Range` возвращает `error{Unsatisfiable}!?struct { u64, u64 }` — три исхода в одном типе:

- `null` — заголовок непонятен, по правилам HTTP его надо не заметить;
- `error.Unsatisfiable` — понятен, но такого диапазона в файле нет: ответ 416;
- пара чисел — диапазон.

Тип читается как фраза, и вызывающий не может перепутать «не понял» и «понял, но нельзя».

### defer и errdefer

```
const file = try dir.createFile("tmp.txt", .{});
defer file.close();

const buf = try a.alloc(u8, 4096);
errdefer a.free(buf);   // только если дальше будет ошибка
try fill(buf);
return buf;             // успех: buf уходит вызывающему
```

`defer` выполняется при любом выходе из блока. `errdefer` — только при выходе с ошибкой. Это решает задачу, ради которой в других языках придумали деструкторы и `finally`: «освободить, если не отдал». Код освобождения стоит рядом с кодом захвата, и порядок обратный порядку захвата — как в стеке.

### Трасса возврата ошибки

В отладочной сборке Zig запоминает путь, по которому ошибка поднималась через `try`. Если `main` вернул ошибку, напечатается не только её имя, но и каждая строка, через которую она прошла. Это не стек вызовов в момент ошибки, а путь её возврата — именно то, что нужно, чтобы понять, откуда она взялась.

### Цена

**Ошибка без данных.** `error.NotNumber` не может сказать, какое именно значение не разобралось. Когда нужны подробности, их передают отдельно: функции загрузки настроек в Клиппере принимают указатель на строку, куда пишут объяснение. Это выглядит как шаг назад по сравнению с языками, где ошибка несёт данные. Причина вынужденная: ошибка в Zig — целое число, и это делает её дешёвой (никаких выделений при ошибке) — а сервер не должен выделять память даже тогда, когда что-то пошло не так.

**`catch return null` легко написать.** Одной конструкцией можно и правильно обработать ошибку, и проглотить ту, которую глотать нельзя. Язык гарантирует, что вы приняли решение, но не что решение верное.

**Накопленная ошибка.** Иногда `try` на каждой строке превращает код в шум. Писатель страниц в Клиппере (`src/out.zig`) не возвращает ошибку при переполнении буфера, а ставит флаг и проверяет его один раз в конце. Это сознательный отход от правила языка, и компилятор за ним уже не следит. Такой приём стоит применять, только когда проверка в конце одна и её нельзя обойти.
