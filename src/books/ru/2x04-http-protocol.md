# Часть II. Протокол и данные

## HTTP/1.1: что сервер обязан уметь

### Что было

HTTP/1.0 (RFC 1945, 1996) — соединение на каждый запрос, без обязательного имени сайта. HTTP/1.1 (RFC 2616, 1999) — то, на чём держался веб 2003 года и держится до сих пор:

- заголовок `Host` обязателен — на одном адресе много сайтов;
- соединение по умолчанию живёт дольше одного запроса (keep-alive);
- запросы можно слать подряд, не дожидаясь ответов (pipelining; браузеры почти не пользовались);
- тело можно передавать кусками (`Transfer-Encoding: chunked`);
- части файла (`Range`) — для докачки;
- условные запросы (`If-Modified-Since`, `If-None-Match`) и ответ 304 — «у вас уже есть»;
- управление кэшем (`Cache-Control`, `Expires`).

Cookie — отдельно: сначала спецификация Netscape (1994), потом RFC 2109 (1997) и RFC 2965 (2000), которые браузеры так и не реализовали полностью; на деле все жили по Netscape.

### Что из этого делает Клиппер

| возможность | в Клиппере |
| Host | обязателен; без него — 400 |
| keep-alive | да; соединение живёт, пока клиент не закроет или не замолчит |
| pipelining | да; несколько запросов в одном пакете обрабатываются по порядку |
| chunked в запросе | нет — 501; формам и загрузкам он не нужен, длина известна |
| chunked в ответе | не нужен: длина ответа известна до отправки |
| Range | да, для скачиваний; суффиксные диапазоны тоже |
| ETag и 304 | для статики и неизменяемых файлов |
| HTTP/2 | нет — 505 |

### Тупой сервер и длина ответа

Самое важное для сервера свойство HTTP/1.1 — что ответ можно отдать с `Content-Length`. Для этого длина должна быть известна до отправки. Сервер, который собирает страницу целиком в буфер и отдаёт одним куском, всегда её знает. Отсюда простота: не нужна кусочная передача, не нужно потоковое формирование, не нужно держать соединение в состоянии «ещё дописываю».

Клиппер собирает каждую страницу целиком в буфер на 6 МБ, вычисляет длину и отправляет заголовок и тело одним системным вызовом. Это возможно потому, что страница 2003 года — законченный документ разумного размера.

### Кэш на стороне браузера

Самый быстрый запрос — тот, которого не было. HTTP/1.1 даёт два способа его не делать:

- **срок жизни** (`Cache-Control: max-age`) — браузер не спрашивает вообще, пока срок не вышел;
- **проверка** (`ETag` и `If-None-Match`) — браузер спрашивает «не изменилось ли», сервер отвечает 304 без тела.

Клиппер отдаёт стили, логотипы и картинки-полосы с долгим сроком жизни и меткой по содержимому. Страницы — без срока: они меняются с каждым комментарием.

### Строгость разбора

Сервер 2003 года часто был снисходителен: принимал `\n` без `\r`, лишние пробелы, кривые заголовки. Клиппер строг: строки — только `\r\n`, заголовок до 8 КБ, у POST должна быть длина. Это не педантизм. Если сервер и прокси перед ним по-разному понимают один кривой запрос, на этом строится атака (подмена запросов в общем соединении). Однозначность разбора — свойство безопасности.

### Чего в HTTP 2003 года нет — и не нужно

HTTP/2 и HTTP/3 ускоряют главное — много мелких запросов через одно соединение. Для страницы, которая состоит из одного документа, одного файла стилей и пары картинок, выигрыш мал. Тупая страница делает быстрый протокол почти ненужным.
