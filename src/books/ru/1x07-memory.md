## Память: распределитель — это параметр

### Вопрос: почему нет `malloc`?

В Zig нет глобального распределителя по умолчанию. Функция, которой нужна память, получает распределитель параметром:

```
fn join(a: std.mem.Allocator, x: []const u8, y: []const u8) ![]u8 {
    const out = try a.alloc(u8, x.len + y.len);
    @memcpy(out[0..x.len], x);
    @memcpy(out[x.len..], y);
    return out;
}
```

Это неудобно ровно один день. Потом оказывается, что по сигнатуре видно, выделяет функция память или нет. Функция без параметра `Allocator` память не выделяет — это гарантия, которую можно проверить чтением. Для сервера, у которого главное свойство «на пути запроса ничего не выделяется», это способ проверить свойство без профилировщика.

`std.mem.Allocator` — интерфейс: указатель на состояние и таблица функций. Любой распределитель можно подставить в любую функцию.

### Распределители стандартной библиотеки

| распределитель | когда |
| std.heap.page_allocator | прямо у системы, страницами; медленно, но без состояния |
| std.heap.ArenaAllocator | много выделений, освобождение всех сразу |
| std.heap.FixedBufferAllocator | выделения подряд из готового буфера; без обращения к системе |
| std.heap.DebugAllocator | ловит утечки, двойное освобождение, обращение после освобождения (в 0.14 переименован из GeneralPurposeAllocator) |
| std.heap.smp_allocator | быстрый распределитель общего назначения для многопоточных программ (появился в 0.14) |
| std.testing.allocator | в тестах: роняет тест при утечке |

### Как это использует сервер

Клиппер при старте выделяет три буфера: арена запроса (24 МБ), тело страницы (6 МБ), готовый ответ (8 МБ). На каждый запрос поверх первого создаётся распределитель:

```
var fba = std.heap.FixedBufferAllocator.init(app.arena_buf);
const a = fba.allocator();
```

Создание — запись двух чисел. Освобождать отдельные куски не нужно: запрос кончился — распределитель забыт, следующий начинает с начала буфера. Забыть освободить невозможно, потому что освобождать нечего; освободить дважды — по той же причине.

### Вопрос: кто владеет результатом?

Это главный вопрос языка без сборщика мусора, и Zig отвечает на него соглашением, видным в сигнатуре. Если функция принимает распределитель и возвращает срез — результат принадлежит вызывающему и живёт столько, сколько память распределителя. Хранилище записей Клиппера возвращает копию значения именно поэтому:

```
pub fn get(l: *Ledger, a: std.mem.Allocator, k: []const u8) ?[]const u8
```

Если бы оно возвращало срез на собственную память, следующая запись того же ключа переписала бы её под ногами у читателя. В Rust такую ошибку не дал бы скомпилировать проверщик заимствований. В Zig от неё защищает только соглашение — и тесты.

### Тестовый распределитель

```
test "без утечек" {
    const a = std.testing.allocator;
    const s = try join(a, "ab", "cd");
    defer a.free(s);
    try std.testing.expectEqualStrings("abcd", s);
}
```

Уберите `defer a.free(s)` — тест упадёт и покажет, где была выделена неосвобождённая память. Утечка перестаёт быть тем, что замечают через месяц по графику памяти.

### Цена

Обращение к освобождённой памяти в ReleaseSafe не ловится ничем. `DebugAllocator` ловит его в отладке, но не в боевой сборке. Это самая большая дыра в безопасности Zig по сравнению с Rust, и закрывают её устройством программы, а не языком: память запроса живёт до конца запроса и освобождается вся сразу, так что «освободили раньше времени» почти негде написать.

Фиксированный буфер — потолок. Запрос, которому нужно больше 24 МБ, не выполнится. Это ограничение, а не защита, и его размер подобран под самую тяжёлую операцию — разбор загруженной книги.
